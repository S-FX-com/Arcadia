## 1. What Arcadia is now

Arcadia is the S-FX staff hub. Any staff member can open it and find what they need about the agency: who works here, how the agency is organized into departments, which clients are active, what services each client has, and who the point of contact is for each one. An assistant, Ask Arcadia, answers questions about all of that, with links back to the records it used.

Shane and his delegated front-office staff (the **Manager** role) set up and maintain the data in **Settings**.

### What Arcadia is not anymore

Arcadia is no longer an accountability instrument, an M365 repository, a doctrine engine, a site planner, or a Cloudflare OS backend. That code is deleted in Phase 1. Git history is the archive; tag the last v5 commit `v5-final` before deleting anything.

### Governing rules (these go into the new `CLAUDE.md` §1)

1. **Arcadia owns its data.** Departments, titles, client records, contacts, services, points of contact, and schedules live in D1 and are edited in Arcadia. Microsoft 365 provides two things only: sign-in (Entra ID) and the staff roster (who exists and whether their account is enabled). Later phases may read M365 *content* (Teams messages) from sources an admin explicitly connects. M365 never supplies structure or configuration.
2. **Read wide, write narrow.** Every active staff member can read everything except areas restricted below. Managers write. Superadmins administer roles and AI settings.
3. **Every mutation is audited.** It writes to `audit_log` with the actor, the action, the subject, and a before/after summary.
4. **Ask Arcadia answers from data, not memory.** Every factual claim about S-FX, a client, or a person comes from a tool result and carries a link to the record. When the data doesn't have the answer, she says so. She does not fill gaps from the model's general knowledge.
5. **Nothing reaches a client automatically.** Arcadia never emails, messages, or posts to a client.
6. **No person-level scoring.** Arcadia does not compute or store performance scores about staff.
7. **Credentials live in one place.** Only modules in `src/integrations/` read secrets or stored credentials. Credentials entered in Settings are encrypted at rest (see Phase 7).
8. **Delete, don't make dormant.** If a feature isn't used, remove it. No feature flags for dead code.

### Stack (unchanged)

- **Runtime:** Cloudflare only. Workers, D1, R2, Durable Objects (SQLite-backed), Queues, Vectorize, Workers AI, and the `agents` SDK.
- **Models:** Anthropic through AI Gateway.
- **Sign-in:** Entra ID OIDC in the Worker (`src/lib/sso.ts`).
- **UI:** keep the existing Preact server-rendered UI and `theme.ts`. A frontend rewrite is out of scope.
  - Small progressive-enhancement scripts are allowed where a form or picker needs them: search-as-you-type, multi-select, and the chat stream.
  - Keep each script small, local, and served by the Worker.

### 2.1 One people table

```sql
CREATE TABLE staff (
  aad_id          TEXT PRIMARY KEY,           -- Entra object id; the stable key everywhere
```

### 2.2 Roster sync (the only structural read from M365)

- Runs daily on a schedule and on demand from Settings → Staff & Roles.
- Reads Graph `/users` member accounts only (`userType eq 'Member'`): `id`, `mail`/`userPrincipalName`, `displayName`, `accountEnabled`.
- Inserts new people as `role='staff'` and updates `email`, `display_name`, `account_enabled`, and `roster_synced_at`. Writes nothing else.
- A disabled account cannot sign in. On login, `resolveUser` rejects a `staff` row with `account_enabled = 0`.
- A login with no `staff` row (roster not yet synced) gets a read-only staff session and triggers a sync.
- Required Graph permission: `User.Read.All` (application). Remove any requested permission no longer needed, and list the final set in `CLAUDE.md` human steps.

## Phase 3 — Departments

### 3.1 Schema (`0004_departments.sql`)

```sql
CREATE TABLE departments (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  slug        TEXT NOT NULL UNIQUE,
  parent_id   TEXT REFERENCES departments(id),   -- NULL = top level
  description TEXT,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  archived_at TEXT,
  archived_by TEXT,
  created_by  TEXT NOT NULL,
  created_at  TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at  TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_departments_parent ON departments(parent_id, sort_order);

CREATE TABLE department_members (
  department_id TEXT NOT NULL REFERENCES departments(id),
  aad_id        TEXT NOT NULL REFERENCES staff(aad_id),
  role          TEXT NOT NULL DEFAULT 'member' CHECK (role IN ('head','member')),
  added_by      TEXT NOT NULL,
  added_at      TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (department_id, aad_id)
);
CREATE INDEX idx_department_members_person ON department_members(aad_id);
```

### 3.2 Rules

- **Nesting.** Depth is unlimited in the data. The UI is designed for 2–3 levels and must still render deeper levels correctly.
- **Moving.** Reparenting rejects cycles on the server. A department can't move under itself or a descendant; test it.
- **Membership.** A person can belong to any number of departments. A department can have several heads.
- **Rollups.**
  - A department's people count = its direct members plus all descendants' members, deduplicated.
  - Display shows "direct" and "including sub-departments" separately.
- **Archiving.**
  - Blocked while the department has non-archived children or active client services (Phase 5). The error says which.
  - Archived departments are hidden everywhere except Settings, where they can be restored.
- **Hierarchy queries.** Use recursive CTEs (`WITH RECURSIVE`), wrapped in `src/departments/tree.ts`. Unit-test it.

### 3.3 Surfaces

**Settings → Departments (`manage_departments`):**
- Tree editor: create, rename, edit description, move (parent select), reorder siblings (up/down), archive/restore.
- Membership panel per department: multi-select people from the roster, toggle head/member, remove.

**Agency → Departments (everyone):**
- Read-only, collapsible tree.
- Each node shows its heads, members (with "includes N in sub-departments"), and description.
- Clients served appear here after Phase 5.
- An **Edit** link to the department in Settings is shown to Managers.

**Profile page:** list the person's departments, marked head/member.

**Directory:** department chips on each person, plus a filter by department that includes sub-departments.

**Done when:**
- Shane can build the real S-FX structure from `departments-seed.md`.
- People appear in multiple departments.
- Tree, rollup, and cycle tests pass.

## Phase 4 — Client CRM (organization-first)

### 4.1 Schema (`0005_crm.sql`)

The existing `clients` table becomes the CRM organization. SQLite cannot widen its `status` CHECK in place, so rebuild it: create `clients_new`, copy, drop, rename, recreate indexes. Then migrate the existing rows:

- `active` and `paused` → `active`
- `offboarded` → `archived`
- `client_bindings` rows are preserved untouched for Phase 9.

```sql
CREATE TABLE clients (
  id                 TEXT PRIMARY KEY,
  name               TEXT NOT NULL,
  status             TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','archived')),
  website            TEXT,
  main_phone         TEXT,
  address_line1      TEXT,
  address_line2      TEXT,
  city               TEXT,
  state              TEXT,
  postal_code        TEXT,
  country            TEXT DEFAULT 'US',
  industry_id        TEXT REFERENCES option_values(id),
  m365_tenant_domain TEXT,                    -- e.g. clientname.onmicrosoft.com or primary domain
  client_since       TEXT,                    -- YYYY-MM-DD
  notes              TEXT,                    -- the general "about this client" field
  archived_at        TEXT,
  archived_by        TEXT,
  created_by         TEXT NOT NULL,
  created_at         TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at         TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE option_values (                  -- Settings → CRM Options
  id          TEXT PRIMARY KEY,
  list_key    TEXT NOT NULL CHECK (list_key IN ('industry','contact_type')),
  label       TEXT NOT NULL,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  archived_at TEXT,
  UNIQUE (list_key, label)
);
-- Seed contact types: Billing, Technical, Decision-maker, General.

CREATE TABLE client_contacts (
  id          TEXT PRIMARY KEY,
  client_id   TEXT NOT NULL REFERENCES clients(id),
  first_name  TEXT NOT NULL,
  last_name   TEXT,
  title       TEXT,
  email       TEXT,
  phone       TEXT,
  mobile      TEXT,
  is_primary  INTEGER NOT NULL DEFAULT 0,
  notes       TEXT,
  archived_at TEXT,
  created_by  TEXT NOT NULL,
  created_at  TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at  TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_contacts_client ON client_contacts(client_id);
-- At most one active primary contact per client:
CREATE UNIQUE INDEX idx_contacts_one_primary ON client_contacts(client_id)
  WHERE is_primary = 1 AND archived_at IS NULL;

CREATE TABLE client_contact_types (           -- a contact can be Billing AND Technical
  contact_id    TEXT NOT NULL REFERENCES client_contacts(id),
  option_id     TEXT NOT NULL REFERENCES option_values(id),
  PRIMARY KEY (contact_id, option_id)
);

CREATE TABLE client_notes (                   -- dated timeline
  id         TEXT PRIMARY KEY,
  client_id  TEXT NOT NULL REFERENCES clients(id),
  body       TEXT NOT NULL,
  author     TEXT NOT NULL,                   -- aad_id
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  edited_at  TEXT
);
CREATE INDEX idx_client_notes ON client_notes(client_id, created_at DESC);
```

**Search.** Add a D1 FTS5 virtual table over client names, websites, and contact names/emails/phones, kept in sync by the service layer on every write. Verify FTS5 support in D1 via the Cloudflare MCP before relying on it, and fall back to `LIKE` if needed.

### 4.2 Rules

- **Active only.** Archived clients disappear from every list, search, and Ask Arcadia answer. They are visible and restorable only in CRM with an "Archived" filter (Manager+).
- **Archiving** a client:
  - ends its active services (Phase 5), with `end_date` set to today and audited
  - stops Enque sync and memory ingestion (Phases 8 and 9)
- **Contacts.** Contacts are always created inside a client. There is no standalone contact creation.
- **Duplicates.** Creating a client whose normalized name matches an existing active one warns and requires confirmation.
- **Notes.**
  - All staff can read notes; Managers can add.
  - Authors can edit their own notes for 24 hours.
  - Edits record `edited_at` and are audited with before/after.
  - Notes are never deleted, only archived by a Manager.

### 4.3 Surfaces

## Phase 6 — Ask Arcadia, rebuilt (global, structured)

The old Ask failed because it answered from a thin doctrine corpus through vector search. The new Ask answers from Arcadia's own structured data **through tools**. Questions like "who is the SEO contact for X" are database queries, not similarity searches.

### 6.1 Architecture

- **Agent.**
  - One Durable Object per conversation, built on the `agents` SDK's chat agent class. Verify the current class name and streaming API in `/reference` or the Cloudflare MCP.
  - The DO stores the message history in its own SQLite.
  - D1 holds a `conversations` index: id, owner `aad_id`, title, `client_id` (Phase 10), created_at, updated_at, archived_at.
- **Transport.** Stream tokens to the browser over the SDK's WebSocket/streaming support, through a small client script in `src/approval/ask.tsx`.
- **Model.**
  - Anthropic via AI Gateway, using the existing `src/ai/router.ts` with a new task kind `ask`.
  - Default to a Claude Sonnet-class model, because tool-use reliability matters more than cost here.
  - The routing and the monthly spend ceiling are configurable in Settings → AI. Enforce the ceiling in AI Gateway and display current spend.
- **Tool loop.** The model calls tools; tools run server-side with **the caller's identity and capabilities**. The model never receives a tool it isn't allowed to use, so the tool list is computed per caller when the conversation starts.

### 6.2 Tools (Phase 6 set — all read-only)

| Tool | Returns |
|---|---|
| `search(query, types?)` | Ranked hits across clients, contacts, staff, departments (FTS) — for name resolution |
| `get_client(id)` | Profile, primary contact, contacts with types, active services with POCs and client contacts, last 5 notes |
| `list_clients(filters)` | Filter by department (incl. children), POC, industry |
| `get_department(id)` | Ancestors, children, heads, members, clients served |
| `get_person(id)` | Title, contact info, departments, POC-for list, education |
| `who_handles(client, department_or_service)` | Convenience: POCs + client-side contacts for a service |
| `recent_changes(since, entity?)` | From `audit_log`: what changed in Arcadia's records |
| `get_schedule(person?, start, end)` | Phase 7 tables, if Schedule ships |

Every tool returns objects with a `url` field for the Arcadia page of the record.

### 6.3 Answer contract

- **System prompt** (in `src/ask/prompt.ts`, versioned):
  - States who Arcadia is and the rules from §1.
  - Requires that every factual sentence cite a tool result.
  - Requires a clarifying question when a name resolves to more than one record.
  - Requires "I don't have that in Arcadia" when tools return nothing.
- **Citations.** The UI renders citations as chips linking to the record. Answers with uncited factual claims fail the eval (6.5).
- **Conversations.** A conversation list in the Ask sidebar: rename, archive. Each user sees only their own conversations; superadmins cannot read others' conversations through the UI.
- **Logging.** Each answer writes `audit_log`: actor, `ask_answer`, conversation id, tools called. Not the full text.

### 6.4 Page

- `/` becomes Ask Arcadia: a conversation pane plus a conversation list.
- Show the CTA in the nav.
- Show suggested starter questions built from real data, e.g. "Who are the POCs for {random active client}?"

### 6.5 Evaluation — required, not optional

- Create `test/ask-eval/` with a seeded fixture database (fake clients, departments, staff) and **at least 40 questions** with expected facts. The questions cover:
  - lookups
  - ambiguity (two clients with similar names)
  - rollups ("which clients does Marketing serve")
  - negatives ("does X have a Billing contact?" when it doesn't)
  - archived clients (must not appear)
  - permission boundaries
- **Unit tests** (CI) check every tool's output against the fixture deterministically.
- **`npm run eval:ask`** (manual, calls the model through AI Gateway) runs all questions and reports:
  - fact accuracy
  - citation coverage
  - false-answer rate on negatives
- **Ship bar:** ≥95% fact accuracy, 100% citation coverage, 0 invented answers on negatives. Record results in `docs/evals/ask-v6.md`.

**Done when:**
- The eval bar is met.
- Ask answers "Who handles SEO for <client>?" in one tool round with linked citations.
- A Staff user cannot see any tool or data restricted to `use_workspaces`.

### 7.1 Spike first (go/no-go)

3. Replace it with PUT.
4. Delete it.
5. Re-read to confirm each state change.
6. Create a time-off entry or read confirmed time off.
7. Confirm what notifications staff receive.
8. Run 100 creates in a batch within throttling limits (`$batch` where supported).

Note: Microsoft deprecated the `MS-APP-ACTS-AS` header for Shifts APIs. App-only calls should not need it. Verify this in the spike rather than assuming. If a call fails, try to explain the failure before concluding.

**If any of steps 1–5 fails and can't be fixed, stop.** Delete Schedule entirely: code, tables (via migration), nav, and Graph permission. Record the decision in `docs/decisions/`. **HUMAN GATE** for the go/no-go call.

### 7.2 If GO: build

**Schema `0007_schedule.sql`.** Replace `shift_patterns` and `shift_pattern_posts` with:

- `shift_rules`: id, `aad_id`, weekdays, start_time, end_time, scheduling_group_id (optional), label, effective_from, effective_to, created_by
  - Optional mapping: Settings → Schedule maps each department to a Teams scheduling group, so a person's shifts land in their department's group.
- `shifts`: id, `aad_id`, date, start, end (stored with the schedule's time zone resolved to UTC), label, source (`rule` or `manual`), rule_id, `graph_shift_id`, `sync_state` (`pending_create`, `pending_update`, `pending_delete`, `synced`, `error`), last_error, updated_by
- Keep `time_off_requests` if the spike showed filing works; otherwise remove the request flow and show time off read-only from Teams.

**Generation.** Rules materialize into `shifts` for a rolling horizon. Default: **the next full calendar month, generated and published by the 15th of the current month**. Both values are configurable in Settings → Schedule. Generation skips dates overlapping confirmed time off.

**Sync job** (daily, plus "Publish now" in Settings):
- Pushes `pending_*` rows to Graph.
- Writes `graph_shift_id` and retries with backoff.
- Surfaces `error` rows in Settings.
- Audits each write.

**Drift policy:**
- Shifts created by Arcadia are authoritative. If someone edits one directly in Teams, the next sync overwrites it and logs the drift.
- Shifts created natively in Teams (no matching `graph_shift_id`) are shown read-only on the Arcadia calendar and never modified.

**Surfaces:**
- **Agency → Schedule** (everyone): week/month calendar from `shifts` and Teams-native shifts, filterable by department and person.
- **Settings → Schedule** (Manager): host Team, department ↔ scheduling-group map, rules per person, one-off edits, publish horizon, sync status/errors.

Delete availability (beta API) code.

**Done when:**
- A rule for one person produces next month's shifts in Teams.
- Editing one in Arcadia updates it in Teams.
- Deleting one removes it.
- A Teams-side edit is overwritten and logged on the next sync.

## Phase 9 — Client memory (Workspaces pipeline)

Goal: every active client accumulates a daily, searchable history from its Enque tickets and its Teams conversations. Ask Arcadia can use that history inside a workspace (Phase 10). Over time this becomes the client history repository.

### 9.1 Spike first — Teams message access (go/no-go per source)

Test app-only Graph v1.0 against the S-FX tenant, with:
- `ChannelMessage.Read.All`
- `Chat.Read.All`
- `Team.ReadBasic.All`
- `Channel.ReadBasic.All`

Record results in `docs/spikes/teams-messages.md`. The questions to answer:

1. Can app-only read messages and replies in a standard channel?
2. Can it read a group chat by id?
3. Does any call fail with a protected-API error?
4. Are **chats with participants from another tenant** (clients' own M365 accounts) readable at all with app-only permissions? Reports say they are not. This decides whether "client chats" means S-FX-hosted channels/chats with client guests, or nothing.
5. What delta or `lastModifiedDateTime` filter is available for incremental reads?
6. What are the throttling limits?

Microsoft's licensing and approval terms for these APIs have changed more than once. Verify against current Learn docs, not notes.

**HUMAN GATE:** Global Admin consent for the new permissions. Shane decides go/no-go per source.

### 9.2 Bindings

- Reuse and rebuild `client_bindings`. Supported types:
  - `teams_channel` (teamId/channelId)
  - `teams_group_chat` (chatId)
  - Enque comes from `client_links`, not a binding.
- Private channels are not bindable.
- 1:1 chats are not bindable.
- **Settings → Workspaces → {client}:** add a binding with a picker (list Teams the app can see, then channels; or paste a chat id with validation); remove a binding; see who added each and when.

### 9.3 Pipeline

- **Daily Workflow per active client** (`agents` SDK Workflow or a Cloudflare Workflow; verify which is current best practice):
  1. Pull new and changed items since each source's cursor.
  2. Normalize them to `{source, external_id, url, author, timestamp, text, thread_id}`.
  3. Write raw JSONL to R2: `clients/{id}/raw/{source}/{YYYY-MM-DD}.jsonl`.
  4. Chunk, embed (Workers AI embeddings), and index.
  5. Generate a **daily digest** with Claude via AI Gateway, routing task kind `digest`: what happened for this client today, with a link on every bullet.
  6. Store the digest in D1 (`client_digests`: client_id, date, body, source_counts, model, generated_at).
  7. Advance the cursors.
- **Index.**
  - Decide between adopting `src/memory/self-hosted.ts` and building a slimmer equivalent, then delete the loser.
  - Requirement: hybrid retrieval (vector + keyword) **filtered by `client_id` at query time**.
  - Use a Vectorize namespace or metadata filter per client in one index. Check current per-index namespace and metadata-filter limits via the Cloudflare MCP before choosing.
  - No cross-client results are possible from a scoped query; write a test that proves it.
- **Retention.**
  - Content is kept while the client is active.
  - Archiving a client stops ingestion. After N days (Settings → Workspaces, default 30), raw R2 data, index entries, and digests are purged, with an export written to R2 `exports/` first.
  - Restoring a client before purge resumes ingestion.
- **Settings → Workspaces:**
  - per-client status: sources, last run, item counts, digest count, errors
  - **Run now**, **Rebuild index**, **Purge**, each confirmed and audited
- **Client page:** a **History** tab (`use_workspaces` only) shows daily digests newest-first, with Enque ticket events interleaved.

**Done when:**
- One real client has three or more days of digests from at least Enque, and from Teams if the spike passed.
- The cross-client isolation test passes.
- Purge removes R2, index, and digest data (test).

## Phase 10 — Workspace mode in Ask Arcadia

- **Entering a workspace.** "Enter a client workspace" appears in Ask Arcadia and on the client page, for `use_workspaces` holders only. It starts a **new conversation pinned to that client**. The `client_id` is set when the conversation is created and never changes; to switch clients, start a new conversation.
- **Scoped tools.** Inside a workspace, every tool is scoped to the pinned client on the server, not by prompt instruction:
  - `get_client`, `who_handles`, `get_tickets`, and `ticket_summary` ignore any other client argument.
  - `search_client_memory(query, since?, until?, sources?)` runs hybrid retrieval filtered to the client.
  - `get_digests(since, until)` returns daily digests.
  - `client_timeline(since)` merges notes, service changes, tickets, and digests in date order.
- **Answers.** Every claim cites a ticket, message, note, or digest bullet with its source link. Questions about other clients get a plain "this conversation is scoped to {client}" and an offer to open a global conversation.
- **UI.** A persistent banner shows "Workspace: {client}" with an Exit button.
- **Eval.** Extend `test/ask-eval/` with at least 25 workspace questions over a fixture corpus: "what did we decide about X last week", "how many tickets about email this quarter", "what changed on the website project". Include isolation questions that try to pull another client's data. **Ship bar:** zero cross-client leakage, ≥90% fact accuracy, 100% citation coverage.

**Done when:** the eval bar is met and Shane can enter a real client's workspace and get a cited answer about the last two weeks of activity.

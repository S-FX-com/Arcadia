# Decision: Arcadia v6 is the S-FX staff hub

**Status:** accepted
**Decider:** Shane Skwarek
**Date:** 9 November 2026
**Supersedes:** [2026-09-27-m365-repository.md](2026-09-27-m365-repository.md), [2026-08-25-pm-first.md](2026-08-25-pm-first.md)
**Brief:** [docs/briefs/2026-11-09-arcadia-v6.md](../briefs/2026-11-09-arcadia-v6.md)

## Context

v4 built Arcadia as an accountability instrument. v5 kept that code dormant and added an M365 repository: a Graph overlay, a tenant Planner index, a Loop catalog, and a weekly run-sheet, most of it superadmin-only. The old Ask Arcadia answered from a thin doctrine corpus through vector search, and it did not answer well.

The result is a large codebase, much of it dormant or gated. Structure the team needs every day (departments, clients, services, points of contact) has no home, because v5 tried to read it from Microsoft 365, which does not hold it.

## Decision

Arcadia is the S-FX staff hub. Any staff member can open it and find who works here, how the agency is organized into departments, which clients are active, what services each client has, and who the point of contact is for each one. Ask Arcadia answers questions about that data, with links back to the records it used.

Arcadia is no longer an accountability instrument, an M365 repository, a doctrine engine, a site planner, or a Cloudflare OS backend.

### Governing rules

1. **Arcadia owns its data.** Departments, titles, client records, contacts, services, points of contact, and schedules live in D1 and are edited in Arcadia. Microsoft 365 supplies two things only: sign-in (Entra ID) and the staff roster (who exists and whether the account is enabled). Later phases may read M365 content (Teams messages) from sources an admin explicitly connects. M365 never supplies structure or configuration.
2. **Read wide, write narrow.** Every active staff member reads everything except restricted areas. Managers write. Superadmins administer roles and AI settings.
3. **Every mutation is audited** in `audit_log` with actor, action, subject, and a before/after summary.
4. **Ask Arcadia answers from data, not memory.** Every factual claim comes from a tool result and links to the record. When the data has no answer, she says so.
5. **Nothing reaches a client automatically.** Arcadia never emails, messages, or posts to a client.
6. **No person-level scoring.** Arcadia does not compute or store performance scores about staff.
7. **Credentials live in one place.** Only `src/integrations/` reads secrets or stored credentials. Credentials entered in Settings are encrypted at rest.
8. **Delete, don't make dormant.** An unused feature is removed. No feature flags for dead code.

### Roles

Three roles replace `superadmin`, `founder`, `lead`, and `specialist`:

| Role | Who | Gets |
|---|---|---|
| `superadmin` | Shane and Alex (seeded) | Everything |
| `manager` | Front-office delegates, assigned in Settings | Everything except granting Superadmin and AI settings |
| `staff` | Every other active roster member | Read access |

Manager is a permission tier, not a reporting line. Department leadership is the separate `head` role on a department membership. `user_capabilities` stays so one person can hold an extra capability, such as `use_workspaces`. `isRepositoryAudience` and every temporary superadmin-only gate go away.

### Delete, don't make dormant

This reverses the 2026-08-25 dormancy decision. Phase 1 deletes the code, tests, routes, bindings, and tables for: doctrine and the old Ask, the escalation ladder, the Certification Ledger, Dispatch enforcement, the operations panel, site planning, the Cloudflare OS bridge and gatekeepers, the Planner objectives index, the Processes/Loop catalog, the run-sheet, the Leadership chart and manager proof, the region map, the delegated M365 connect, the placeholder pages, and the workspace membership gating. The memory engine (`src/memory/driver.ts`, `self-hosted.ts`, `ingest.ts`) stays until Phase 9 adopts it or deletes it. Schedule, Continuing Education, Directory (minus the map), model routing, `src/ai/`, and sign-in stay working.

Git history is the archive. The last v5 commit is tagged `v5-final`.

### D1 moves to wrangler migrations

`src/schema/d1.sql` becomes `migrations/0001_baseline.sql`, verbatim. Every later schema change is a numbered migration file. Destructive migrations (DROP, table rebuilds) are applied by Shane, by hand, after he runs `scripts/export-d1.sh`. The CI deploy job does not apply migrations. It fails if any remote migration is pending, so schema stays ahead of code and the human gate holds.

### Phase order

```
0 → 1 → 2 → 3 → 4 → 5 → 6 → 8 → 9 → 10
                 └──── 7 (Schedule) any time after 2
```

0 resets the spec and migrations. 1 deletes v5. 2 builds staff, roles, and Settings. 3 departments. 4 the client CRM. 5 services and the Clients Overview. 6 rebuilds Ask Arcadia over structured data through tools. 7 Schedule. 8 the integrations framework and Enque. 9 client memory. 10 workspace mode in Ask Arcadia.

Phase 6 ships before any M365 or Enque content ingestion on purpose. If Ask is not useful on structured data, it will not become useful with chat history added. That is worth learning before Phases 8 and 9 are built.

### Go/no-go gates

- **Schedule (Phase 7).** Keep Schedule only if Arcadia can author shifts and keep Teams Shifts updated reliably. A spike against a test Team must read the schedule, create a published shift, replace it, delete it, and confirm each change. If any of those fails and cannot be fixed, Schedule is deleted: code, tables, nav, and Graph permission. Shane makes the call.
- **Teams messages (Phase 9).** A spike tests app-only reads of standard channels and group chats, protected-API errors, cross-tenant chats, incremental filters, and throttling. Shane decides go/no-go per source after Global Admin consent.
- **Enque (Phase 8).** No Enque code is written until Shane puts Enque's API documentation, or a link and a test key, in `docs/vendor/enque/`. Endpoints are confirmed from the docs and a live call, not guessed. If there is no incremental filter, the cheapest alternative is proposed before building.

## Consequences

- `CLAUDE.md` is rewritten for v6 from §1–§3 of the brief. The v5 history-and-rationale sections do not carry over.
- `ASK-ARCADIA.md` is deleted. Phase 6 replaces it.
- Each phase is one branch (`sfx/v6-phase-N-<slug>`) and one PR, merged before the next phase starts.
- The accountability instruments are gone, not sleeping. Bringing accountability back later means a new decision and new code, not flipping a flag.
- Graph permissions shrink to `User.Read.All` for the roster in Phase 2. Schedule's existing consent stays until Phase 7 decides. Schedule and Teams-message permissions are consented for their spikes and kept only if the spike passes. A failed spike removes the Graph permission along with the code.
- Cloud resources orphaned by Phase 1 are not deleted by code. `docs/teardown-v5.md` lists the `wrangler` commands, and Shane runs them.
